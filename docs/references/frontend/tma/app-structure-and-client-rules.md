# TMA app structure and client rules

Canonical client structure rules for planned `apps/tma`.

## Scope

Use this doc for:

- workspace/package placement
- folder ownership
- router/bootstrap boundaries
- SDK package-line choice
- TMA UI-system defaults

For canonical TMA UI and navigation rules, see [native UI and navigation pattern](native-ui-and-navigation-pattern.md) and [TMA Design](../../../../apps/tma/DESIGN.md).

## Stack defaults

- Use React + Vite SPA.
- Use React Router for in-app history.
- Use TanStack Query for server state.
- Use Zustand for small client-local workflow state.
- Use Framer Motion for screen, sheet, and high-touch interaction motion.

## SDK package-line rule

Telegram Mini Apps packages changed across package families over time.

Rules:

- Use the `@tma.js/*` line for new runtime work.
- In React code, prefer `@tma.js/sdk-react` as the default app-facing dependency.
- Pull in lower-level `@tma.js/*` packages only when the React package does not already expose the needed surface cleanly.
- Do not mix multiple Telegram Mini Apps package families in one client.
- If a slice intentionally deviates from the `@tma.js/*` line, record the concrete blocker in the plan and keep the migration boundary explicit.

## Package boundary

Place the client in a separate workspace package:

```text
apps/tma/
  src/
    app/
      bootstrap/          # init, providers, app shell
      router/             # router creation, route shells, eager route imports
    features/
      <domain>/
        api/              # households keeps api/
        components/
        hooks/
        model/            # e.g. expenses/model, auth/model
        pages/            # route components live here (no routes/ folder)
        stores/
        types/
        utils/
    components/
      shared/             # project-owned wrappers and behavior components
      ui/                 # pristine shadcn-generated output only
    lib/
      telegram/           # SDK wrappers only
      auth/
      query/
      storage/
      i18n/
    utils/
```

Rules:

- Do not add TMA runtime code under `apps/web`.
- Do not import feature or UI code from `apps/web/src`.
- Reuse only shared DTOs, extracted pure helpers, and worker API contracts.
- Do not fork domain rules between web and TMA.

## Import direction

Allowed:

```text
src/main.tsx -> app/bootstrap/*
app/router/* -> features/*/pages/*
features/* -> feature-local components/hooks/api/stores/types/utils
features/* -> components/shared or components/ui when reuse is real
lib/telegram/* -> raw Telegram SDK packages
```

Forbidden:

```text
feature/page/component -> window.Telegram.WebApp direct calls
components/ui -> feature code
generated components/ui -> Telegram or product behavior
shared component -> domain-specific feature component
apps/tma -> apps/web/src imports
```

## Shell ownership

Keep shell responsibilities explicit:

- Root app shell owns bootstrap gates, providers, viewport/safe-area setup, and fatal launch/auth failure UI.
- Route shells own route composition, eager route imports, and route-level guards.
- Flow shells own `BackButton`, closing-confirmation, and multi-step flow state wiring; in-page generated shadcn `Button` components, composed by `TmaHapticButton` when needed, own flow CTAs.
- Leaf components render feature UI. They do not own Telegram global chrome.

## Router rules

- All in-app navigation stays inside SPA history.
- Use `navigate()` or `Link` only.
- Full-page route changes with `window.location` are a bug for TMA flows.
- TMA routes use eager static imports. Do not use `React.lazy`, `Suspense` route fallbacks, or route-level code splitting.
- If BrowserRouter is used, deployment must include SPA fallback rewrites. Do not rely on 404 recovery.

## UI-system rules

- TMA uses shadcn/ui with Base UI, generated by pinned `shadcn@4.18.0` from exact preset `b6GzOWK7U` (Sera, olive/yellow, Geist Mono, Lucide).
- Every shadcn file in `src/components/ui` remains unmodified preset output. Do not put TMA props, defaults, haptics, classes, or behavior in generated files.
- `TmaHapticButton` lives outside `components/ui` and composes the pristine generated Button. `NativePicker`, `DatePicker`, and `QueryState` also live outside `components/ui` and retain their behavior.
- TMA UI is fixed light-only. Do not sync the visual theme to Telegram theme vars.
- Do not apply a dark root class or dark token override, and do not alter generated dark branches.
- Restore preset Geist Mono as the global app typography; do not override it with a system body stack.
- Do not use Telegram `BottomButton` or `MainButton`; use in-page generated shadcn `Button` CTAs, with `TmaHapticButton` for the standard haptic wrapper.
- Project-owned components should own amount entry, bottom sheets, segmented tabs, and finance-specific interaction states.
- There is no native Telegram tab bar, title header, or bottom sheet. Build those as web UI.

## Styling

Tailwind CSS v4 remains the styling substrate. Legacy `--tma-*` UI tokens are transitional only and are removed after all consumers migrate. Generated shadcn output stays in `components/ui` and remains untouched; project-owned wrappers and behavior components compose it from `components/shared` or feature-owned locations. Use the [native UI and navigation pattern](native-ui-and-navigation-pattern.md) and [TMA Design](../../../../apps/tma/DESIGN.md) for current component and visual rules.

## State placement rules

- TanStack Query owns worker-backed data.
- Zustand owns short-lived multi-step flow state only.
- Local component state owns presentational UI state.
- Do not mirror server DTOs into long-lived client stores without a real offline/resume need.

## Performance defaults

- Load route code eagerly; keep startup light with narrow auth bootstrap data and route intent first, deferring only non-critical server data, not route modules.
- Keep animation, safe-area, and keyboard behavior inside the shared shell layer, not re-solved per page.

## Verification rules

- Prefer unit tests for wrappers, helpers, stores, and flow reducers.
- Verify route, keyboard, safe-area, and in-page CTA behavior in Telegram-like mobile WebView conditions.
- Record which launch modes and device classes were checked in harness evidence.
